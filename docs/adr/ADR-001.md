# ADR-001 — SQLite FTS5 como único store de busca/indexação

- **Status:** Accepted
- **Data:** 2026-07-29
- **Decisores:** Maintainer / Lead Architect (DCE)
- **Tags:** storage, search, offline, performance

---

## Contexto

O DCE precisa indexar conhecimento corporativo heterogêneo e recuperá-lo com baixa latência, 100% offline, sem APIs pagas, sem banco vetorial e com footprint adequado a máquinas de desenvolvedores.

Há pressão cultural da indústria para “RAG + embeddings”. Isso conflita com os requisitos não negociáveis do produto.

## Decisão

Usar **um arquivo SQLite por workspace**, com:

- tabelas relacionais para metadados e filtros;
- **FTS5** para busca full-text (BM25);
- SQL explícito via repositório (sem ORM no horizonte inicial).

Não introduzir vector DB, extensões de embedding, nem serviços cloud de search.

## Alternativas consideradas

| Alternativa | Prós | Contras | Por que não |
|-------------|------|---------|-------------|
| SQLite + extensão vetorial | Similaridade semântica | Complexidade, modelos, drift, requisitos de IA | Viola “sem vector / sem IA externa” |
| Elasticsearch / OpenSearch | Relevância madura | Operação pesada, não offline-first no laptop | Overkill |
| Whoosh / Tantivy (lib) | FTS dedicado | Mais uma base; sync com metadados | SQLite já une metadados + FTS |
| Grep sobre arquivos | Zero infra | Sem ranking, metadados, pacote de contexto | Não atende o produto |
| PostgreSQL FTS | Robusto | Servidor externo; foge do “arquivo local” | Complexidade operacional |

## Consequências

### Positivas

- Zero rede na consulta
- Backup = copiar arquivo
- Metadados + texto no mesmo motor transacional
- Testes de integração simples (`tmp_path`)
- Alinhamento total aos requisitos offline

### Negativas / trade-offs

- Sem similaridade semântica densa (sinonímia limitada)
- Qualidade depende de âncoras, boosts e boa indexação de campos
- FTS português pode exigir dicionário/sinônimos técnicos
- Índices muito grandes exigem disciplina de o que indexar (ex.: Git)

### Mitigações

- RetrievalPlanner baseado em âncoras (`ORA-*`, issue keys)
- Campos boost (title, tags, codes)
- Budget e quotas por fonte
- Documentação honesta: lexical + estruturado, não “mágica semântica”
